4. 干净克隆后的开发构建

在目标平台/架构使用 Node 24.x（至少 24.9.0）、Git、Python 3.10+。首次准备需要访问依赖源；严格内网应在获批环境准备离线材料，按构建指南搬运。不可在 Windows 上直接交叉生成可验收的麒麟桌面应用。

git clone https://github.com/xddzb/neiwang-xiaozhi.git
cd neiwang-xiaozhi
npm ci
npm run prepare:runtime
npm run build
npm start

APP 校验命令及实际 builds 目录名见 BUILD_AND_RUN.md。先用根目录开发构建验证环境，再有选择地迁移快照改动；不要把 R11.2 bootstrap 或加密文件直接覆盖开发版。开发版凭据位于 data/dsh/.credentials.yaml，R11.2 发布版使用 data/config/*.enc，两者配置格式和生命周期不同。

5. R11.2 离线发行流水线

  1. 以原 R10-Modular 核心/插件资产为发行基线；该大体积基线未入库。release-scripts/build_kylin_r112.py 修改版本、恢复 AI 表格读写及移除菜单。
  2. 组织内网预配置：configure_kylin_internal_model.py 在获批的本地环境注入模型和 RAG 加密 seed。模型 Key 从环境读取，Dify seed 从原受控发行目录读取；GitHub 无任何 seed。
  3. fix_kylin_shell_newlines.py 规范所有 Shell 为无 BOM 的 LF，并同步 pack.json 中 payload 的 SHA256。
  4. restore_kylin_rag.py 补齐早期漏装的 dify.enc，生成小补丁和修正分包。
  5. package_kylin_rag_full.py 校验分包后合成完整归档，生成 SHA256。历史脚本路径以原工程根目录为基准，不是在快照文件夹直接执行。

公开脚本中的内网地址已替换为示例，接手方须在组织本地恢复实际配置。复现字节相同的旧交付包需要原有发行基线、依赖版本、加密配置和原构建环境；本仓库不声称仅凭快照即可复现该二进制。

6. RAG 缺失事故与修复

原因：发布打包统一排除 config/defaults，后续内网预配置只回填 model.enc，漏掉 dify.enc。应用复制默认配置的逻辑本来支持两个文件。因此模型可用，但知识库显示未配置。

修复：组织发行流水线同时注入两个 seed；首次启动复制到 data/config，已有文件不覆盖。已有安装可使用本地“麒麟RAG配置恢复补丁”，退出应用后解压、执行恢复脚本，重启并打开左下角 RAG，再新建会话。补丁不改模型、机器人凭据或绑定。通用公开源码不应携带组织 seed。

排查顺序：检查 data/config/dify.enc 是否存在 → 使用随包 Python 3.11 运行 rag_tool.py status → 检查 RAG 开关 → 在组织网络检查 Dify DNS/TLS/权限 → 经用户授权做一次真实 query。configured 只证明配置可读取，不证明请求已成功。

7. 凭据和迁移

  • 本快照已将原固定共享加密密钥替换为 NEIWANG_CONFIG_KEY。它必须是组织自行生成并安全保存的 32 字节密钥（64 位十六进制），同时提供给 Python 和 Node；不要上传。
  • 本仓库不提供原共享密钥或加密 seed。快照不能直接解密旧发行包配置；迁移时应由授权操作员重新录入模型/Dify配置，或在受控旧环境导出后用新密钥重加密。不要打印到聊天或日志。
  • data、机器人 Client Secret、管理员绑定、用户聊天、DWS token/账号授权、SSH 私钥、业务接口正文、代理密码和含凭据发行包均不入库。
  • 机器人的组织管理员、应用权限管理员、APP 内绑定管理员是不同角色；交接须分别确认，不把扫码登录视为自动获批。

8. 钉钉 Stream 一直重连

收到的实际诊断显示 api.dingtalk.com、oapi.dingtalk.com、wss-open-connection.dingtalk.com 均 DNS ENOTFOUND，且没有代理；token 与 gateway 请求尚未成功。优先排查组织 DNS、出口代理/放行及 TLS，修改绑定码无法解决该网络故障。钉钉客户端消息同步不代表第三方机器人接口拥有相同网络通道。

Stream 需要 APP 主动访问钉钉 HTTPS 和 WebSocket 服务，不需要开放本机公网入站端口。完全离线时应由组织提供获批专用接口/中转；不得擅自搭建跨网桥。多个电脑使用同一机器人是额外风险，但这份诊断没有证明存在该问题。
